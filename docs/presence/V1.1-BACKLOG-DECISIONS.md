# V1 "remaining feature backlog" — value decisions (closed)

Evaluated the 8 non-blocking backlog items against **what's already built** and **product fit**. Reuse-first: several were already delivered under other names. Outcome: **nothing here needs building** — 4 already done, 2 won't-build, 2 deferred (owner/infra-gated). Backlog closed.

| # | Feature | Verdict | Evidence / reason |
|---|---|---|---|
| 1 | Weekly client digest | **Defer → V1.1** | Email infra exists (`sendEmail`, `brandEmailShell`, live scheduler) but no digest composer. Value is real only *with* email sending, which is owner-gated (Resend domain verify). Building it now would duplicate the Timeline page until email is on, and add a scheduled-send path best designed at activation time. Small, reuse-heavy build (reuses the Timeline/Attention/Insights adapters + `brandEmailShell`) to do **when email is turned on**. |
| 2 | Auto-notify on approvals | **✅ Already done** | Notifications derive from the event log — `lib/notifications.ts` maps `approval_requested`/`approval_decided` to human labels; `handleNotifications` (studio) + client-visible approval events (bridge) + the CMS-UX-6 **Approval Center** surface them to both sides in-app. *(Email push of approvals = V1.1, owner-gated.)* |
| 3 | Shareable preview links | **✅ Already done** | `POST /preview/share-link` mints a signed, time-limited link; `handleSignedPreview` + `handlePublicPreview` serve pre-auth, expiry-checked previews (`routes/preview_env.ts`). |
| 4 | Per-item shared comments | **Won't build** | Client↔studio communication is already covered by project **messages**, **shared relationship notes**, and **approval decision notes**. A per-item comment thread would be a new parallel interaction surface for low incremental value — against the frozen "no new workflows / no duplicate systems" rule. |
| 5 | Named snapshots / version comparison | **Naming ✅ done; comparison won't build** | Named versions ship via `version_label` (`POST /publishes/:id/label`), surfaced in **Snapshot History**. Version-to-version *comparison* is low value for a non-technical owner (they don't diff old editions); the `describeChanges` diff engine is available if that ever changes. |
| 6 | Published-site uptime monitoring | **Point-in-time ✅ done; continuous → V1.1** | "Is your site online" is already checked live in **Website Health** (HTTPS probe via the launch checklist). Continuous monitoring + alerting needs periodic cron probes + storage + alert delivery (email, owner-gated) — real infra, V1.1, not a beta blocker. |
| 7 | Public third-party API | **Won't build (ever)** | Wrong product fit: the audience is non-technical business owners and the entire ethos is "you never touch the tech." A public API is high security/support surface for near-zero customer value, and contradicts the calm/invisible positioning. The only "SDK" is the internal industry-pack author surface, which is appropriate. |
| 8 | Per-page SEO / meta overrides | **✅ Already done** | Fully rendered: per-page `noindex` + sitemap exclusion, **and** per-page title/description overrides — `page_seo` is applied by the template renderer via `seoOv(...)` on offerings/about/faq/contact/updates (`templates/business-classic/1.0.0/render.ts:460`). Settable via the settings API (`page_seo`, `pages_noindex`). |

## Summary
- **Already built (4):** auto-notify on approvals · shareable preview links · named snapshots · per-page SEO/meta. Verified in code.
- **Won't build (2):** per-item comments (parallel workflow, low value) · public third-party API (wrong fit, security surface).
- **Deferred to V1.1 (2):** weekly client digest (owner: email activation) · continuous uptime monitoring (infra + email). Both reuse-heavy and non-blocking.

No new build was warranted. The platform already covered the valuable parts of this backlog.
