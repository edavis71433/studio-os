# L3 — Presence Optimization Engine (Foundation)

Studio OS continuously observes a customer's digital presence and identifies where it can be improved — search visibility, AI-search readiness, accessibility, speed, foundations, measurement, local presence, trust, imagery, and business knowledge. **The customer never has to understand SEO, Core Web Vitals, structured data, accessibility, DNS, or indexing.** The engine understands these systems; the pipeline (downstream) explains them in plain business language.

This milestone is the **Foundation**: it formalizes the optimization engine as a unified, extensible provider architecture and fills coverage gaps. It does **not** turn optimization observations into customer-facing recommendations — that is L3.1 (Optimization Judgment Depth), deliberately out of scope.

## The engine already ran — L3 made it a foundation

The observation layer existed before L3: 15 base providers (M9.0) + 12 optimization providers (M10), all implementing one pure `Provider` contract in a single registry that the frozen Evidence Engine executes. L3 did four things, all additive:

1. **Formalized** the architecture into a unified, area-organized engine (`optimization/engine.ts`) with an explicit provider→area map and live introspection.
2. **Filled coverage gaps** with seven new evidence-only observations.
3. **Extended the collector** with two probes (CAA, CDN fingerprint).
4. **Documented** the contract, the area map, and the extension model.

Nothing was rebuilt. Rebuilding would have duplicated a working system — which the milestone explicitly forbids.

## The pipeline (nothing bypasses it)

```
Observation (collectors, I/O)
  → Evidence   (pure providers emit measured facts)
  → Judgment   (rules turn evidence into findings + audience + timing)
  → Recommendation → Business Moments → Concierge
```

Every optimization capability is a provider feeding **Evidence**. Providers never judge, rank, summarize, or write customer copy — the pipeline owns all of that. This is why an optimization provider can never "leak" a recommendation: the only thing it can do is `emit()` an evidence type that already exists in the catalog.

## The provider contract

```ts
Provider = { name: string; provide: (input: ObservationInput, emit) => void }
```

- **Pure** — no I/O, no clock, no randomness; `input.now` is the only time. (All probe I/O lives in collectors: `evidence/collect.ts`, `optimization/collect.ts`.)
- **Evidence-only** — emits via `emit(type, surface, resource, facts)`. `emit` throws if the type isn't registered in the catalog, so a provider physically cannot invent an observation vocabulary.
- **Isolated** — the registry runner guarantees a throwing provider contributes nothing and poisons no other. Failure isolation is structural, not hoped-for.
- **Catalog-driven copy** — `severity`, `confidence`, `next_action`, and both plain-language sentences (`human`, `tech`) live in the catalog. The provider carries only measured facts. So "customer language" is never generated by a provider.

## The ten optimization areas (`optimization/engine.ts`)

| Area | Purpose (plain language) | Example providers |
|---|---|---|
| Search visibility | Be found when people search | `seo`, `technical_seo`, `metadata`, `links`, `structured_data` |
| AI search readiness | Be quotable by AI assistants | `aeo` |
| Accessibility | Work for every visitor | `accessibility`, `accessibility_deep` |
| Speed | Load fast enough to keep visitors | `performance`, `performance_deep`, `lazy_loading` |
| Foundations | Keep domain/security/email sound | `website`, `infrastructure`, `email_auth` |
| Measurement | Understand visitors (observation only) | `analytics` |
| Local presence | Show up right on maps/directories/reviews | `local_presence`, `local_presence_deep`, `reviews`, `reputation` |
| Trust | Signals that say the business is real | `trust`, `trust_deep` |
| Imagery | Real, well-made images that load well | `media`, `visual_assets` |
| Business knowledge | Site facts agree with the owner's documents | `knowledge` |

The core Presence providers (`business_info`, `content`, `conversion`, `freshness`) feed the same Evidence Engine but observe the room's content and accuracy, not the optimization lens — so they're declared core, not orphaned.

**Introspection:** `GET /admin/optimization` (staff) returns `describeEngine()` — every area, the providers serving it, and its observation vocabulary — derived live from the registry + catalog, so it can never drift from what actually runs.

## L3 gap-fill observations (evidence-only)

Seven observations added across the areas, each: a provider emit + a catalog entry + membership in exactly one judgment rule.

| Type | Area | What it observes |
|---|---|---|
| `seo.noindex` | SEO | a page telling search engines not to index it |
| `seo.twitter_card_missing` | SEO | home lacks Twitter/X card tags for rich previews |
| `performance.cdn_absent` | Speed | no CDN edge headers/server token (single-origin serving) |
| `performance.lazy_loading_missing` | Speed | 4+ images, none deferring off-screen load |
| `infrastructure.caa_missing` | Foundations | resolving domain with no CAA record |
| `accessibility.table_structure` | Accessibility | a data table with no header cells |
| `local_presence.apple_business_unconnected` | Local | Apple Business Connect not connected (honest absence) |

New collector probes: a DoH **CAA** lookup (`OptDns.caa`) and a **CDN fingerprint** from response headers (`homeProbe.server`/`cdnHint`).

## Evidence-only, and awaiting judgment (the L3.1 boundary)

Every optimization observation — the M10 twelve *and* the L3 seven — is currently mapped to the `platform_roadmap` judgment rule with `audience: 'none'`: **recorded and always suppressed.** This satisfies the completeness law (every catalog type maps to exactly one rule — the "no silent gaps" invariant) while keeping optimization evidence from surfacing as customer recommendations before the deliberate rules exist. **Promoting these observations into audienced, timed, plain-language recommendations is L3.1 (Optimization Judgment Depth) — a separate, deliberate rules change, never a side effect of observing more.**

## The extension model (adding a provider — no architecture change)

1. Write a pure `Provider`; append it to `OPTIMIZATION_PROVIDERS` (`optimization/providers.ts`).
2. Register any new evidence types in the catalog (`optimization/catalog.ts`) — severity/confidence/human/tech/next_action there, measured facts in the provider.
3. Map every new type to exactly one judgment rule. Foundation-stage → the suppressed `platform_roadmap` rule; customer promotion is a later deliberate change.
4. Map the provider to its area in `PROVIDER_AREA` (`optimization/engine.ts`).
5. Put any new probe I/O in a collector (never in a provider).
6. Add a test (isolation + emit/no-emit).

That's the whole checklist. No engine change, no schema change (evidence `type` is free-text validated by the catalog; the categories already exist). The engine is built to grow this way indefinitely.

## Tests

`tests/presence/optimization_engine_test.mjs` — 20 checks: each gap-fill observation fires on its trigger and stays silent otherwise; every new type is evidence-only and pipeline-compatible (catalog + judgment completeness); the engine's ten areas are complete, mapped, and introspectable with no orphaned providers; composability, isolation, and determinism hold with the additions.
